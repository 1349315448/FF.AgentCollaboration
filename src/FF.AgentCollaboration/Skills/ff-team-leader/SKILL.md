# 话题组长

红旗由用户设置。开始组队或接任时查当前话题的 `kb_team_context`，从返回的路径读计划和名册。知识库停用时，用 `list_windows(detail=true)` 核对成员，在对话和关联回信中完成交接。

## 分工和团队记忆

- 在 `PLAN.md` 写清目标、验收条件和依赖。每项工作注明负责人、当前进度、下一步和证据位置。已有成员能承担时直接分工；需要新伙伴时，与用户商定职责后提交 `propose_team_agents`，等工作台返回用户确认结果再派活。
- 分派用 `send_to_agent`。把返回的消息 ID 记在对应任务旁，独立任务设 `supersedePrevious=false`。按原编号处理澄清和交付，收到最终回信后核对验收条件，再更新总计划。已加入的外部成员沿用原授权，组长发出的跨端任务由请求方工作台接收回执和获准附带的 Markdown。
- 总计划保留固定的「成员任务记录」入口。用 `kb_team_context` 返回的 `taskRecords.arguments` 调用 `kb_search`，可按关键词检索、用 `limit` 和 `offset` 翻页，再用 `kb_read` 读具体记录。成员开工、更新进度时目录自动反映变化。只在分工、依赖、验收或团队决策变化时编辑总计划；先读当前版本，写回带 `expectedVersion`。遇到版本冲突，重读后合并仍适用的改动。
- 名册与分工归话题。更新 `TEAM.md` 时保留平台生成的成员段。经过验证、后继组长会用到的决定写进团队记录，并链接成员提交的证据。自己的排查技巧用 `scope=agent` 放在个人 `tasks/`。按需调用 `read_knowledge_skill`；更新已有文档先读原文，写回时带 `expectedVersion`。

## 审批与维护跨端协作

1. 打开「小组 → 小组合作」，默认全组参与。短期借调可指定一个或多个成员，并设权限、次数或有效期。外部合作由对方接受邀请并提交本组，发出邀请的一方核对后确认。组长负责管理，可以由其他获准成员负责收发。
2. 申请方与审批方分别由本机用户确认本组参与名单、入站读写权限、附件和次数。选择名单前讲清必要职责和交付物。红旗组长参与协作，也可直接接任务。成员名单由现任组长核对，授权通过工作台操作。
3. `list_windows(detail=true)` 中的 `permanentGroup` 条目携带小组、节点名和 `target`。派发时使用 `target`，写明项目、目标和验收条件。已获准的组员可以直接交流。需要新成员参与时，请双方确认各自名单后再分派。
4. 在总计划记跨组依赖、负责人和原消息 ID。原回信地址和 `replyTo` 将结果关联到双方群聊。通过 `document` 附证据，遵守对端文件开关和入站权限。信息先在本组核对，仅向已关联小组发送明确点名的内容。
5. 外部合作换组长后请用户在「小组合作」核对成员并保存。合作暂缓时暂停，结束时解除对应小组。收尾前确认未交付任务和回执，保留原计划和已同步记录。

## 交出组长职责

成员退出或换人时，在总计划更新负责人，保留原任务编号和已提交的记录。接手者在自己的目录续写，原成员的记录继续作为交接依据。

1. 用户准备移交且你仍持红旗时，在现有总计划中补一份简短快照：已验收事项、在办事项的原消息 ID 和负责人、阻塞及待决定的问题、交付链接、接下来应先做什么。续办同一计划即可。
2. 接任者已确定时，把快照位置及最紧急的待办发给对方。标明哪些在途回信仍会送到你这里。用户在工作台完成移交后，用 `read_team_skill` 切到组员操作；若移交先于整理，直接把已知情况作为组员回报给新组长。

## 从组员接任

1. 先核对红旗和当前名册，再读原计划、交接记录及最近交付。保留自己尚未做完的任务和原编号，在计划中写明继续负责还是需要改派。
2. 按原消息 ID 核对每个在办项。只向进度或负责人不明的成员询问；原组长离线时，由计划、成员记录和已有回信恢复现场。没有证据的项标为待核实，保留原任务，避免重复执行。
3. 更新同一份总计划，写明接手时间、未决事项和下一步。向受影响成员确认后续协调人。已发出的请求沿用原回信地址；需要接手的旧回执，由原发件人或执行成员转告结论并附原编号。结案时把验收结果和遗留项写入 `SUMMARY.md`。
